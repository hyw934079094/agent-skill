# 真实业务测试输入输出协议 v1

## 1. 适用范围与交接约定

在项目或目标模块已实现、开始新增/审计/修复真实业务测试时使用。规则约束见仓库 rule.md、project-rule-template.md；发现与覆盖检查项见 [checklists.md](checklists.md)。本协议规定交接内容，不要求新建测试平台、执行器或数据库。

同一任务可在一份 Markdown 记录内依次维护五个阶段；不强制拆成五个文件。每阶段保留以下公共字段：

- protocol_version: 1；task_id: 任务唯一标识；project_ref: 仓库、分支与提交 SHA；scope: 目标模块与排除范围。
- artifact_id: 当前输出标识；input_refs: 上游输出标识与版本；stage: project / business / data / execution / failure。
- status: ready（该阶段最小内容齐备）/ blocked（缺少必要信息）/ not_applicable（说明不适用依据）。
- evidence: 文件路径与符号/行号，或执行命令、日志、查询结果等可追溯位置；不得写入凭据与个人敏感数据。
- unknowns: 未确认事项、影响、确认方式；next_action: 下一步动作或具体待答问题。

ready 只表示阶段可交接，不表示业务测试通过。未知值写“未确认”，不以空白、推测或默认值冒充事实。源代码表现与业务期望冲突时保留二者及证据，先澄清受影响断言。只阻塞依赖缺失事实的部分，独立且已确认的范围可继续。
恢复任务时先复用同一提交和范围下的现有记录；提交、配置、业务入口或数据条件变化时更新受影响阶段及下游引用，旧执行结果保留历史，不作为新版本通过证据。

## 2. 项目识别（project）

**触发条件：** 首次接手项目；仓库/目标模块/提交变化；原记录缺少运行条件。
**输入：** 用户目标、仓库与目标提交、全部适用规则和 skill、项目结构、构建配置、运行配置及现有测试。
**输出：** 项目识别记录，供 business 阶段使用。
**最小内容：**

- 项目类型、语言/框架、模块边界、目标范围及对应发现证据；未找到组件记录搜索范围。
- 构建/启动/测试命令、工作目录、环境配置名、必要依赖与访问条件；区分“从配置推导”与“实际验证可用”。
- 数据库、缓存、消息、定时任务和外部系统清单；不适用项说明依据。
- 已有测试位置、运行方式及真实性审计：核心 Mock、断言、顺序/环境依赖、数据污染、清理缺口；没有测试也明确记录。
- 待确认信息与阻塞范围；已有测试的问题在扩展相关覆盖前修复，不能直接计入可信覆盖。

**进入下一阶段：** 范围及可分析入口已明确；缺少运行环境可继续静态业务提取，但不得声称已经执行。

## 3. 业务入口与状态流（business）

**触发条件：** 项目识别完成；新增业务范围；入口、权限、状态、事务或副作用变化。
**输入：** project 输出、需求/接口说明、入口代码、Service 调用链、枚举/实体、表结构、事务和事件实现、已有测试审计。
**输出：** 带 flow_id 与 case_id 的业务流及覆盖表，供 data 和 execution 使用。
**最小内容：**

- 每条 flow_id 的入口（API 方法与路径、Service 方法、事件消费者或定时任务）、角色/权限、前置条件、输入约束和业务目标。
- 状态流：原状态 → 动作/条件 → 目标状态；非法流转的拒绝结果及数据应保持不变的范围；无状态字段时说明，并列业务步骤。
- 调用链、核心/关联表、关键字段、事务边界、回滚预期、缓存/MQ/其他副作用；异步完成条件与等待上限。
- case_id 对应 flow_id、场景类别、操作步骤、业务期望、观测方式及证据；覆盖主流程、分支、异常、阻塞、边界、一致性、事务、幂等性，不适用项写原因。
- 既有可信覆盖、新增/修复范围、未覆盖原因；业务期望必须有依据，不将代码现状自动当作正确期望。

**进入下一阶段：** 目标用例的合法前置状态、操作和可观测断言已确定；语义不明的用例保持 blocked。

## 4. 测试数据（data）

**触发条件：** 执行用例前；数据前置条件、环境或生成/清理方案变化。
**输入：** project 运行条件、business 用例与状态流、环境隔离能力及数据接口。
**输出：** data_plan_id 对应的数据生成与闭环方案；实际创建后记录受影响资源标识。
**最小内容：**

- case_id、环境、独立测试账号/角色、唯一命名或运行标记、前置数据与来源。
- 创建步骤：优先真实 API/Service/业务流程，记录调用顺序、参数来源和创建后验证；禁止直接伪造中间状态。
- SQL 初始化仅限正常流程无法提供的合法基础数据；说明必要性、约束校验和覆盖限制，不得绕过被测业务校验或状态流。
- 隔离与重跑策略、创建/修改资源清单、修改前快照或恢复依据。
- 成功、断言失败、执行中断三种情况下的清理/恢复动作、执行时机与验证方式；独立提交、异步消费者和外部副作用不能仅靠测试事务回滚处理。
- 不可恢复资源与处理方案；缺少闭环能力时标记受影响用例 blocked，不能先污染环境再补方案。

**进入执行阶段：** 环境可用，前置数据合法，清理/恢复可实施；方案 ready 不代表数据已经创建。

## 5. 执行结果（execution）

**触发条件：** 每次实际执行，包括重跑；请求交付但无法执行时也输出结果记录。
**输入：** project、business、data 的明确版本及测试实现、运行环境。
**输出：** run_id 对应执行记录，失败或异常转 failure 阶段。
**最小内容：**

- 提交 SHA、环境/config 名、测试实现位置、命令与工作目录、开始/结束时间、退出码；未启动时记录原因，退出码标为不适用。
- 每个 case_id 的结果：passed / failed / blocked / skipped / not_run；期望值、实际值、状态/数据库/关联数据/副作用断言证据。
- 计划与实际执行数量、各状态数量及 case_id 清单；汇总数量须一致。not_run 用于未执行，blocked 用于缺少必要条件，skipped 须记录跳过依据。
- 测试框架成功与业务断言结论分别记录；HTTP 200、进程退出 0 或生成测试代码均不能单独证明业务通过。
- 数据资源标识、清理/恢复的实际结果及残留验证；清理失败时保留用例原结果，同时将本次运行闭环状态标为失败。
- 实际覆盖、未覆盖/未执行范围与原因、剩余风险；允许报告部分通过，禁止将其扩大为整个模块通过。

异步断言须记录完成判据、等待上限和观测结果；超时必须报告，不能通过无限等待隐藏问题。

## 6. 失败复盘（failure）

**触发条件：** 业务断言失败、环境/依赖阻塞、异步超时、清理/恢复失败，或已有测试审计发现不可信覆盖。
**输入：** run_id（审计未执行时写不适用及审计引用）、case_id、关联业务流和数据方案、日志/异常/调用链、状态及事务证据。
**输出：** failure_id 对应复盘记录；修复后以新 run_id 回连原失败。
**最小内容：**

- 失败步骤、期望与实际、最小复现方法、受影响模块/业务范围及风险依据。
- 归因类别：业务实现 / 测试实现 / 数据方案 / 环境配置 / 外部依赖 / 业务期望待确认 / 未确定；允许多项，不强行单一归因。
- 已证实事实、根因假设、支持/反对证据、下一项验证动作分别记录；证据不足写“根因未确定”。
- 调用链、状态流和事务/异步边界中的失败位置；说明是否存在部分提交、残留数据或重复副作用。
- 修复或后续动作及原因；不能删断言、跳过失败点、篡改数据、隐藏失败来换取通过。
- 重跑范围、回归风险、清理结果、新 run_id 与结果；未重跑标为未验证，无法解决保留阻塞与待确认问题。

## 7. 最小交接模板与验收

以下为结构模板，不是执行证据；复制后填入真实内容。用例/数据/运行/失败可以各用一张小表表达。

```yaml
protocol_version: 1
task_id: <任务标识>
project_ref: <仓库 / 分支 / 提交SHA>
scope: <目标范围；排除范围>
artifact_id: <阶段输出标识>
input_refs: [<上游标识与版本>]
stage: <project|business|data|execution|failure>
status: <ready|blocked|not_applicable>
evidence: [<可追溯证据位置>]
unknowns: [<未知事项、影响、确认方式>]
next_action: <下一动作或具体问题>
# 按本阶段“最小内容”补齐正文
```

交付前确认：

1. project → flow_id/case_id → data_plan_id → run_id → failure_id（如适用）可追溯，重跑不会覆盖原失败。
2. 目标用例有真实业务期望和证据，执行、未执行、跳过与阻塞已区分。
3. 创建与修改的数据均有闭环方案和实际执行状态；残留与清理失败已显式报告。
4. 根因未确定、业务未确认、未重跑与未覆盖内容仍保留，不用“全部通过”替代。
